# Change-detector test inventory

Baseline: merged main at `c44c8b5`. The scan covered **82 test files, 551 test declarations** (parameterized declarations counted once), and **2,091 expectation calls**. There were no snapshot API assertions. The change detectors were ordinary source/prose substring checks, identity checks, and implementation-specific interaction assertions.

This is a reviewed inventory of candidate clusters, not an automatic claim that every exact assertion is bad. The question is: **would this test fail after a harmless refactor while the contract it claims to protect still works?**

## Deliberately retained

- **Effect boundaries:** argument-safe process invocation, target repository/run IDs, mutation ordering, no calls after rejection/disposal, and no forbidden effects. Mock assertions are useful when they observe these boundaries, not private choreography.
- **Safety and boundedness:** resource limits, cancellation, sandbox isolation, immutable injected capabilities, escaping, terminal control filtering, stale revisions, atomic writes, rollback, and preservation of unrelated files.
- **Public representations:** wire-frame fields, persisted user-authored source/data, pagination, reflection signatures, native/source discrimination, and deliberate absence of private handlers or invented source.
- **User-visible rendering:** meaningful identity, content, outcomes, omissions, indentation, width, and lifecycle behavior. Testing emitted output is not the same as reading implementation source. Exact byte assertions remain appropriate where the bytes are the contract, such as terminal-control sanitization.
- **Documentation consumers:** README/emitted-code examples that must compile, resource discovery, and budget/accounting behavior. These test whether the material is usable rather than whether it contains a prescribed sentence.
- **Dedicated policy gates:** formatting, generated-contract drift, architecture, and package-layout checks. This pass covers the Vitest suite; it does not silently weaken those independent gates or their coverage thresholds.

Reviewed false positives included function metadata/inspection, source parsing, storage and promotion, layered registries, capability argv preparation, sandbox dispatch/wire handling, renderer sentinel checks, and formatter fallback fidelity. Their source-like strings are inputs or public outputs, not inspections of implementation text.

## Counterfactual checks

Temporary Vite transforms exercised the actual rewritten guest suite **without changing production files on disk**:

- Replacing `pitCall(JSON.stringify` with the semantically equivalent `pitCall (JSON.stringify` left all six tests passing. The removed literal-token assertion would reject this formatting-only change.
- Replacing delivered guest results with `null` failed five tests, including the new round-trip and input-semantics cases. The suite still detects incorrect behavior rather than merely accepting any generated program.

Production source and trusted helper implementations are unchanged by this cleanup. New tests use the existing injected-helper harness or small compiler/VM consumers; there is no new runtime behavior to accept through the TUI.

## Rule for future tests

State the contract in the test name, vary inputs so wrong attribution or dropped data cannot hide behind identical fixtures, and assert observable results/effects. Prefer semantic equivalence over private names, whitespace, object identity, or incidental ordering. If a test only proves that a file contains its own implementation or repeats policy prose, delete it or move the genuine invariant to the gate that owns it.
